# 0003 初版数据库用 SQLite，服务单实例部署

状态：已采纳
日期：2026-10-09
关联：T-008、T-009、T-017

## 背景

设计书第 12 节把数据库列为待确认（SQL Server、MySQL 还是 PostgreSQL）。评估后发现数据量不是决定因素：

| 数据 | 规模 |
| --- | --- |
| 画布预设、模板、版本、素材元数据、调用方、用户 | 几百到几千行，基本不增长 |
| 调用日志 render_log | 按每天 2 万次调用（批量算一行）估算：一年约 730 万行、2～3 GB；保留 180 天常驻约 360 万行、1 GB 左右 |

开放接口的热路径不访问数据库（模板、调用方都在内存里），数据库性能不影响单张 100 ms 的目标。日志按设计由后台批量写入，写入压力很小。

真正的约束是部署方式。2026-10-09 确认：**前期不考虑高可用**，单实例部署可以接受。单实例的设计容量（4 核 8 GB，每秒 60 次）对一个工厂足够。

## 决定

- 初版用 SQLite（EF Core 的 SQLite Provider），服务单实例部署。
- 数据目录由配置 `LabelService:Data:Directory` 指定，默认程序目录下的 `data/`。里面两个库文件和素材目录：
  - `label.db`：画布预设、模板、版本、素材元数据、调用方、后台用户。
  - `label-log.db`：调用日志。单独一个文件，日志批量写入不会和后台保存模板抢写锁。
  - `assets/`：图片、图标、字体文件，表里只存元数据。
- 每个连接打开时设置：`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。这些 PRAGMA 集中写在一处连接初始化代码里。
- 表结构用 EF Core 迁移管理，启动时自动升级。
- 调用日志保留期可配置，默认 180 天，每天清理一次（T-009）。
- 备份：每天用 `VACUUM INTO` 生成快照到备份目录，保留最近若干份（T-017）。不要直接复制正在使用的 .db 文件。
- 数据访问只通过 EF Core，不写 SQLite 特有的 SQL（上面的 PRAGMA 除外），为以后换数据库留余地。

## 备选方案

- SQL Server：公司常用，支持多实例和高可用，有成熟的备份体系；但要单独的数据库服务器、账号和运维，初版用不上多实例。
- MySQL、PostgreSQL：和 SQL Server 一样需要单独部署，没有额外收益。

## 影响

- **服务只能单实例运行。** 数据目录不能放网络共享盘（文件锁不可靠，会损坏数据），也不能让两个服务进程同时使用同一个数据目录。设计书里的“多实例横向扩展”改为后期能力。
- 以后需要高可用或多实例时换 SQL Server：换 EF Core Provider、重新生成迁移、写一次数据迁移脚本，估计一到两天。届时写新的 ADR 取代本篇。
- EF Core 的 SQLite Provider 在查询里比较、排序 `DateTimeOffset` 和对 `decimal` 做聚合有限制。时间列统一存 UTC 的 `DateTime`，不用 `DateTimeOffset`。
- 检查程序每次用临时数据目录，跑完删除。
- Docker 部署要把数据目录挂成卷（T-017）。
