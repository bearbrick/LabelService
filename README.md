# 标签生成服务（LabelService）

一个独立的标签生成服务：在网页设计器里拖拽画出标签模板（文本、一维码、二维码、图片、图标、线、矩形），定义数据字段；业务系统（MES、WMS、ERP）传“模板编码 + JSON 数据”，服务返回可以直接打印的 PNG、PDF 或 ZPL 文件。另外提供给第三方用的 .NET SDK 和 WinForms 调用演示程序。

核心性能指标：单张标签服务端处理 P95 ≤ 100 ms。

## 三个部分

仓库分成前端、后端、调用端三个文件夹，各自独立编译、独立检查，互不引用项目，只通过 HTTP 和模板 JSON 交互（[ADR 0004](docs/adr/0004-three-parts.md)）。

| 文件夹 | 内容 | 技术 | 入口 |
| --- | --- | --- | --- |
| [frontend/](frontend/README.md) | 网页设计器、管理后台 | Vue 3 + TypeScript + Vite + Konva | `package.json` |
| [backend/](backend/README.md) | 契约、渲染引擎、服务端 | .NET 10、ASP.NET Core、SkiaSharp、SQLite | `LabelService.Backend.slnx` |
| [client/](client/README.md) | 调用端：SDK、WinForms 演示程序 | .NET（SDK 兼容 .NET Framework 4.6.2） | `LabelService.Client.slnx` |

```
LabelService/
```

## 路线图

这一节给评估和排期用：初版还要做什么、哪些留到二期、以后能往哪里扩展、还有哪些问题要先定。每项工作的验收标准、可以改的文件和当前状态，以 [docs/tasks](docs/tasks/README.md) 里的任务文件为准。

“规模”是相对大小，用来排优先级：**小**是一两天能做完的独立功能；**中**涉及几个文件或需要验证效果，三到五天；**大**是一整块界面或交互，要两周以上。按一个人全职、不算 AI 协作的加速估算。

### 二、初版明确不做（二期候选）

设计书第 1 节划在初版之外的功能。架构上都留了位置，排进二期时不需要推倒重来。

| 功能 | 为什么初版不做 | 以后怎么做 | 规模 |
| --- | --- | --- | --- |
| 服务直接送打印机 | 现场打印机、网络、驱动差异大，先由调用方负责 | 做一个装在现场电脑上的“打印代理”，SDK 里已有网络打印和 Windows 打印队列的代码可以复用 | 中 |
| 发号（序列号、流水号） | 服务端保存计数器要处理并发和防重号，容易出错 | 按模板或业务维护计数器，生成时原子递增；单实例 SQLite 下实现简单，多实例要靠数据库锁 | 中 |
| 模板嵌套（画板套画板） | 初版的 A4 拼版已经覆盖“同一个标签排满一张纸”；把不同模板组合成一个模板的需求较少 | 新增“嵌入模板”元素，锁定子模板版本；发布时展开成普通元素，生成性能不受影响（T-020） | 中～大 |
| 表格元素、按条件显示 | 交互和排版规则复杂 | 新增表格元素，给元素加“显示条件”属性；都属于向后兼容的契约变更 | 中～大 |
| 原生 ZPL 指令、TSPL | 初版用位图 ZPL，中文和图片不依赖打印机，效果和 PNG 一致 | 新增输出格式：原生 ZPL（`^FD`、`^BC`，文件小、传输快）、TSPL（TSC 等品牌） | 中 |
| 异步批量任务 | 初版单次最多 500 张，同步返回 | 提交任务、查询进度、下载结果；超过上限的大批量走这条路 | 中 |
| 多租户 | 初版只服务本公司 | 模板、调用方、日志按租户隔离 | 大 |
| 高可用、多实例 | 前期不需要（ADR 0003） | 换 SQL Server（估计一到两天），模板缓存加跨实例刷新，前面加负载均衡 | 中 |

### 三、可扩展方向

初版之外，按价值大小列出的扩展方向。“现在的预留”说明当前代码已经为它准备了什么。

**设计能力**

| 方向 | 内容 | 现在的预留 | 规模 |
| --- | --- | --- | --- |
| 更多元素 | 圆、椭圆、多边形、富文本（一个文本框里多种样式） | 每种元素一个绘制器，在登记表加一行（`IElementPainter`） | 小～中 |
| 计算字段 | 有效期 = 生产日期 + N 天、数量换算、字段拼接和截取 | 绑定语法 `{{key:format}}` 可以扩展成表达式 | 中 |
| 公共组件 | 公司 Logo、地址栏等做成组件，多个模板引用，改一处全部更新 | 和模板嵌套（T-020）是同一套机制：发布时展开 | 中 |
| 多语言标签 | 同一模板按语言切换文字（出口唛头常用） | 字段定义可以加语言维度 | 中 |
| 版本对比 | 两个模板版本并排显示差异 | 版本内容是完整 JSON，可以直接比对 | 小 |

**输出与打印**

| 方向 | 内容 | 现在的预留 | 规模 |
| --- | --- | --- | --- |
| 更多打印机语言 | 原生 ZPL、TSPL（TSC）、EPL、Godex 等 | 每种格式一个输出文档，在登记表加一行（`OutputDocument`） | 每种中 |
| 打印代理 | 浏览器或业务系统一键打印到现场打印机，带打印队列和打印机状态 | SDK 的 `NetworkPrinter`、`WindowsRawPrinter` | 中 |
| RFID 标签 | 打印的同时写入 RFID 芯片（ZPL `^RF` 指令） | 依赖原生 ZPL 输出 | 中 |
| 打印记录与补打 | 记录谁在什么时候打了什么，按记录一键补打 | 调用日志已有请求号；补打需要另存业务数据，初版按设计不存，由调用方重新调用 | 中 |
| 移动端、PDA | 手持终端扫码后打印 | 开放接口是普通 HTTP + JSON，任何终端都能调 | 中 |

**数据接入**

| 方向 | 内容 | 现在的预留 | 规模 |
| --- | --- | --- | --- |
| Excel / CSV 批量打印 | 后台上传表格，按列对应字段，批量生成 | 批量接口（T-007）+ 字段定义 | 小 |
| 数据源连接器 | 模板直接配置取数（SQL 查询或 HTTP 接口），调用方只传单号 | 字段定义已是“key + 类型”，取数层可以放在校验之前 | 大 |
| 回调通知 | 异步批量完成后回调业务系统 | 依赖异步批量任务 | 小 |

**接入与生态**

| 方向 | 内容 | 现在的预留 | 规模 |
| --- | --- | --- | --- |
| OpenAPI 文档 | 自动生成接口文档，Swagger 页面在线调试 | 请求、响应、错误码都已集中定义 | 小 |
| 其他语言 SDK | Java、Python 等；可以从 OpenAPI 自动生成 | 契约见 `docs/contracts.md`，.NET SDK 可以作为参考实现 | 每种中 |
| 统一登录 | 对接公司统一登录（SSO） | 管理后台的鉴权和开放接口的 API Key 是分开的 | 中 |
| 模板导入导出 | 模板在测试环境、生产环境之间迁移，或分享给其他工厂 | 模板就是一份 JSON | 小 |

**复用到其他课题**

| 方向 | 内容 | 现在的预留 | 规模 |
| --- | --- | --- | --- |
| 用户自定义报表、单据打印 | 送货单、出库单等 A4 单据，复用设计器和渲染引擎，再加表格元素和分页 | 渲染引擎和设计器与“标签”业务无关，按纸张尺寸渲染 | 大 |
| 模板发布审批 | 模板发布前走审批流程，可以接入 OA 审批流 | 草稿和发布本来就分开（T-008） | 中 |
| AI 辅助设计 | 上传现有标签的照片或 PDF，自动识别生成模板；或用文字描述生成模板 | 模板是结构化 JSON，适合由模型生成，再在设计器里微调 | 中～大 |

## 快速开始

需要 .NET SDK 10.0.100 以上、Node.js 20.19+ 或 22.12+；WinForms 演示程序需要 Windows。

一次验证全部三个部分（编译、格式检查、检查程序、前端打包，并临时启动后端跑 SDK 端到端检查）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\verify.ps1
```

启动后端服务（`http://localhost:5080`，开发环境自带测试 Key `lbl_test_local_dev`），另开一个终端生成一张箱标：

```powershell
dotnet run --project backend/src/LabelService.Server
curl.exe -o box.png -H "X-Api-Key: lbl_test_local_dev" -H "Content-Type: application/json" --data-binary "@backend/samples/requests/box-label.render.json" http://localhost:5080/api/v1/render
```

响应头 `Server-Timing` 会列出服务端每个阶段的耗时。前端和调用端的命令见各自的 README。

## 参与开发

这个仓库计划由多个 AI 助手和人一起开发。**不管是人还是 AI，动手前请先读 [AGENTS.md](AGENTS.md)**：里面有硬性规则、协作流程、完成定义和常用命令。简单说：

1. 每项工作对应 `docs/tasks/` 下的一个任务文件，先认领再动手，做完写交接记录。
2. 一般只改一个部分；改模板 JSON、接口、错误码属于契约变更，三个部分和文档要一起改。
3. 交付前运行 `verify.ps1`（或只验证改动的部分：`-Part backend`、`-Part client`、`-Part frontend`）。

代码风格沿用公司 DB Studio 的约定：中文 XML 注释、4 空格、CRLF、控制台检查程序；提交信息用英文 Conventional Commits。
